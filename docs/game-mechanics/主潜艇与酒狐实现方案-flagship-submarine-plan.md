# 唯一主潜艇与酒狐船长实现方案

2026-10-14。目标平台为 Minecraft 1.21.1、NeoForge 21.1.259；以工程实际启用的 Create 6.0.10、Aeronautics 1.3.2、Sable 2.0.6、Deep Seas 3.3.0、Power Grid 0.6.2 为基线。本文件是实现方案，不代表潜艇、备份或酒狐已完成开发。接口与来源见 [Mod 能力核对](潜艇相关Mod能力核对-submarine-mod-capability-research.md)。

主潜艇是玩家和 AI 船长酒狐长期共同生活、改装和探险的家。建议采用 **Sable 载体与物理、航空学装配和控制、Deep Seas 潜航系统、自研唯一性与档案管理** 的组合。单独保存潜艇档案是可行方向，但日常运行仍交给 Sable 与世界存档管理；独立档案负责版本、事务和恢复，不能成为另一套同时驱动物理的运行世界。

## 玩家体验与首版边界

首版按一个世界或服务器共同拥有一艘主潜艇设计，跨维度仍是同一艘。多人共享主艇，船长、驾驶员、工程师拥有不同权限；未来的小艇、子艇、敌对舰船不占用主艇身份。这个范围是本方案建议默认值。

游戏循环为：与酒狐确定目标 → 检查船况和补给 → 出海调查与解决问题 → 受损抢修或返航 → 船坞改装 → 进入更深、更远或更危险的海域。主艇外形和设备可以改变，名称、身份、航海经历和酒狐记忆持续保留。

首台建议采用单主船体、分舱、固定设备架构。暂不采用多层嵌套载体、可脱落动力舱和复杂可变形机构，先让保存与恢复闭环稳定。外观可按约长48～64、宽17～23、高17～23格预留，均为设计范围；须以装配限制、实际方块数、密闭检测成本、吃水和试航结果确定最终尺寸。现有128×128船坞容得下这个静态外包络，但不能据此承诺回转、下潜与全部物理行为已验证。

船内预留驾驶与酒狐终端、生活舱、动力舱、左右压载系统、供氧与应急舱、货舱、出入口和后续工具/武器接口。先做可驾驶、可潜航、可维护的主艇，再逐步填入战斗与任务功能。

## 现有能力与自研分工

| 功能 | 复用基础 | 本项目开发内容 |
| --- | --- | --- |
| 方块船体、位置、姿态、速度、质量、重心 | Sable 的 sub-level 与物理接口 | 读数适配、船况面板、主艇及其组成部分的登记 |
| 装配与拆解、传感器、红石操控 | 航空学包中的 Simulated，Create 的动力与控制元件 | 船坞操作流程、改装权限、装配校验和回滚 |
| 水下推进、压载、供氧与密闭舱 | Deep Seas | 设备布局、报警汇总、工程任务与难度配置 |
| 材料耐压、裂纹、破舱进水 | Deep Seas 的船壳配置和压力系统 | 科技材料分级、玩法阈值、损毁判定与日志；不重复叠加同一压力伤害 |
| 定深及跟随海床高度 | Deep Seas 艇载电脑、声呐、泵控制器 | 酒狐下达目标、控制权切换、异常时接管 |
| 电路、发电和电气故障基础 | Power Grid | 分区断电、关键负载清单、维修提示、保存恢复适配 |
| 唯一主艇、改装事务、独立档案、一键部署 | 自研为主，复用 Sable 序列化原语 | 全部业务规则、重启恢复、旧艇作废与防复制 |
| 酒狐人格、记忆、任务、航线、协同战斗 | 现有机械和控制系统作为执行端 | 船长逻辑、路线规划、任务编排、目标与射击规则 |
| 洋流速度锁、通行尺寸锁 | Sable 的运动、形状和施力能力 | 海流场、逆流评估、完整船体扫掠检查 |

这里的“继承”以调用接口、适配器和组合为主，不直接继承或复制对方整套船体实现。物理质量和速度以 Sable 为准；玩法上的耐压等级、任务状态、酒狐关系和维修记录由自研模块管理。质量不等于最大航速，最大可达航速要由推进、阻力、海流和配置共同决定。库存、燃料是否影响质量必须按现有动态质量支持实测，不能默认箱子装满就会变重，也不能把已计入物理的质量再加一遍。

## 唯一主艇的身份

世界级登记表保存稳定的 `vesselId`、所有权、当前状态、设计版本及恢复代次 `generation`。Sable 的 UUID 是当前载体的物理身份，两者分开：改装重装或恢复可以分配新的 Sable UUID，但仍然是原来的主潜艇。

一个主艇可能包含主船体、轴承上的活动部件、连接的子载体和胶水实体。登记为带有部件角色的组成图，记录每部分的局部坐标和连接关系；不简单把附近所有载体都算作主艇。靠泊连接的码头、临时靠近的子艇和玩家身上的物品均有明确边界。

建议状态包括未建造、船坞停泊、改装中、验证中、航行、严重受损、确认损毁、恢复中、停放或未加载、待核对。只有服务器能够转换状态。所有玩家的部署请求通过同一个主艇锁串行处理。

拆成多个碎片时，碎片记录来源 `vesselId + generation`，不自动获得新的主艇资格。旧代次在恢复提交后永久失效；已加载旧艇清退，未加载碎片登记作废标记，在后续加载时处置。未经核对的主艇失联不能直接点击复制。

## 单独保存哪些数据

采用每个世界内部的独立目录，避免不同存档误用同一艘艇：

```text
<世界存档>/dbv/vessels/<vesselId>/
  manifest.json                 身份、数据格式、版本与恢复代次
  designs/<revision>/           船坞验收通过的结构与设备布局
  checkpoints/<checkpointId>/   同一时点的船体、设备和资源状态
  transactions/<transactionId>/ 改装或恢复事务、材料托管账
  journal/                      损伤、航行和资源变更记录
  captain/                      酒狐身份、记忆、关系与任务引用
```

路径是拟定格式。大型船体数据用压缩 NBT，索引和便于审查的元信息用 JSON。世界级 SavedData 保存唯一主艇索引；档案清单记录世界ID、schema版本、MC/NeoForge/Mod版本和校验和。不直接覆盖或移动正在运行的 Sable 区块文件。

| 数据类别 | 保存内容 | 恢复原则 |
| --- | --- | --- |
| 船体结构 | 方块状态、方块实体、局部坐标、船壳材料、舱门、设备位置 | 按验收版本恢复；不得漏掉方块实体数据 |
| 活动结构 | 子载体、胶水、轴承结构、约束、相关非玩家实体 | 收集完整连接图；恢复时重映射身份和坐标 |
| 资源 | 容器、流体、燃料、弹药、储能及外部交换记录 | 按明确恢复政策结算，防止复制和回档刷物资 |
| 第三方状态 | 电线端点、红石频率、压载量、供氧、裂纹和进水记录 | 使用专门适配器；可重算的缓存重建，不能假定都在普通方块NBT中 |
| 航行状态 | 位置、维度、姿态、速度、任务、故障 | 记录供追溯；船坞恢复强制安全姿态、零速度和停机，不照搬事故瞬间速度 |
| 酒狐与主线 | 人格标识、关系、记忆、已知地点、任务里程碑 | 与结构回滚分离；修艇不能让酒狐忘记旅程或重复发奖励 |
| 玩家 | 船员归属和必要的安全位置记录 | 不复制玩家实体，不回滚玩家背包、经验或整个世界 |

Sable 2.0.6 的船体序列化会保存 plot 中的方块、方块实体和部分调度数据，但所查 `ServerLevelPlot.save()` 没有将所有普通实体收进同一个返回标签。因此一个 `toData()` 调用不等于完整潜艇档案；必须补齐实体、连接及第三方状态，并做往返恢复测试。

## 船坞改装与失败回滚

建议改装按一笔可以提交或撤销的工程处理，不做随机失败。漏水、超限、设备缺失、动力不足、装配错误或玩家取消才导致验证失败；优先显示具体问题并允许继续修改。

1. 进入船坞操作界面，检查权限、泊位空闲、船速、战斗状态和所有组成部分是否已加载。停止 AI、武器、推进及自动生产，断开岸电/物流等外部连接，把人员移到安全位置。
2. 固定船体，建立一致的改装前快照；完成落盘、校验与读取检查后才开放改装。备份失败就不进入施工阶段，保持原艇可用。
3. 改装在明确的船坞范围内进行。首版优先保持 Sable 船体身份并对其固定，减少反复拆装带来的坐标问题；需要转换为静态方块时，先实现受控拆装适配，不能把普通拆解当作事务保障。
4. 提供对称参考、尺寸边界、重心显示、材料清单、舱室密闭检查、接口标记、变更对比和错误定位。WorldEdit 可作为工程师工具，但其 undo 不是主艇回滚系统。
5. 限制不支持保存的方块/实体、超范围结构、重复主控核心、断开的关键部件以及越权操作。存储、管道、机械臂和其他自动化都不能跨越改装托管边界偷偷转移物品。
6. 验证尺寸与泊位、完整性、舱室、材料耐压、供氧、推进/压载、质量与重心、能源和控制通道。质量与推力给出建议和试航结果，不用单个重量阈值冒充物理验证。
7. 验证通过后建立新设计版本和新检查点，提交材料账本，再解除停机。失败或取消时恢复改装前状态，并按托管账结算新增、拆下和暂存材料。

材料应通过船坞工程仓托管：拆下物品暂存，新用材料预留，提交后结算，取消后归还。不能一边把拆下的发动机带走，一边恢复含发动机的旧快照。首版没有封闭资源交换和回滚测试之前，不开放可带走物品的生存改装。

## 实时监控和损伤

“实时监控”指持续读取与响应，不是每个 tick 将整艘大艇写入磁盘。建议初始预算：轻量驾驶数据在安全的物理/服务器阶段读取，仪表约5次/秒同步；健康汇总约每秒一次；结构变化走事件和脏标记队列。舱室检测尽量复用 Deep Seas 的分步扫描，附加检查限制单 tick 工作量，实际频率以性能采样为准。

| 面板 | 内容 |
| --- | --- |
| 航行 | 对地速度、后续对水速度、深度、姿态、角速度和预定航线 |
| 结构 | 船体完整性、最弱耐压部位、裂纹、破口、脱落部件 |
| 生存 | 各舱进水、密闭、供氧、可用逃生路线 |
| 机电 | 推进和泵状态、供电、关键设备离线、资源余量 |
| 档案 | 最近成功检查点、设计版本、写入失败、当前是否可恢复 |

伤害分为碰撞、超深破裂、爆炸/敌袭、电气故障与自研特殊环境伤害。复用现有破坏结果，新增任务与报警反馈。统一“健康度”只是概览，不能替代关键舱失效或失去操控的真实判定。已安装 Sable 不等于已经启用了清单中的独立碰撞伤害附属。

当前已查到 Deep Seas 内爆酝酿入口，可作为危急记录触发点；普通爆炸和方块更换也应接入。NeoForge 的玩家挖掘事件覆盖不了压力系统直接销毁方块等全部路径。对缺少公开事件的路径使用隔离的版本适配，必要时限定 Mixin；首版列出明确覆盖范围，不能承诺拦截所有第三方删除行为。

## 四类备份与恢复政策

| 档案 | 触发时间 | 用途 |
| --- | --- | --- |
| 验收设计 | 船坞建成或改装成功 | 保留可重建的完整结构与安装设备配置 |
| 改装前快照 | 每次开放施工之前 | 完整撤销本次工程，包含材料事务 |
| 出航检查点与滚动记录 | 出航前、稳定安全时、资源/结构变化时 | 保留最近一致的运行状态及变化历史 |
| 危急事故记录 | 内爆酝酿、严重进水、关键系统失效、受控删除之前 | 固化事故信息和能及时取得的状态，不能覆盖最后完好设计 |

首版全量备份主要在停泊和出航前短暂静止时完成。海上可先做轻量记录与有限检查点；之后实现带结构版本检查的增量快照。候选的30～60秒周期和保留数量只是配置起点，不是性能承诺。持续变化的多个区块不能跨 tick 随意拼成一个“完整时刻”；需短暂冻结、写时复制或有一致性边界的增量机制。

服务器线程或经同步的物理安全阶段读取并深拷贝状态；后台线程只压缩写入不可变副本。临时目录写完、校验、刷盘后再提交清单指针，保留上一有效版本；跨文件提交需要事务日志和启动恢复，不能只依赖某个文件 rename。磁盘不足或写入失败要显示可恢复到哪个时点。

“损毁前备份”不能只等最后一帧：瞬间爆炸、崩溃、断电或其他 Mod 删除可能不给足时间。可靠恢复依据是预先落盘的有效检查点；危急记录用于尽力缩小丢失窗口。实际丢失窗口是最近成功提交点到事故之间的时间，不对未完成落盘的内容作保证。

建议区分两种恢复语义：

- **改装失败**：恢复到改装前，包括本次工程的资源结算。
- **出海损毁**：按最近验收设计重建主艇，保留酒狐与任务进度；货物、燃料和弹药单独结算，默认不凭设计图补满。重建价格、冷却、保险和物资保留比例属于待定玩法参数。

如果希望损毁后连货物都恢复到事故前，必须先做完整资源账本：处理船内外转移、战利品领取、死亡掉落与残骸打捞，确保同一资源只保留一份。首版可先使用空货舱或全部货物托管模式验证，不能先上线任意背包回档再补防复制。允许打捞可重复补回的设备和船壳也会复制资源，需纳入重建成本或在恢复时使对应残骸失效。

## 船坞一键部署

界面上可以只有一个“恢复主潜艇”按钮，后台必须完成以下过程：

1. 服务器核实主艇确实可恢复，不是未加载或暂时失联；获取主艇与泊位锁，记录事务。
2. 校验档案完整性、Mod及方块兼容、材料/费用条件、船坞碰撞空间。缺失方块不静默变空气，失败时不扣除材料。
3. 将旧代次作废，处理旧艇、碎片、掉落和库存权属；必要时进入待核对状态，阻止旧艇与新艇同时可用。
4. 在保留的泊位按指定朝向部署停机船体，重建实体与连接，重映射第三方坐标引用，重新扫描密闭舱和物理质量。
5. 验证唯一性、结构、设备、货物结算与安全出生位置。成功后原子提交新代次和物资扣除，酒狐恢复值守模式；失败则撤销临时部署，保留原档案与费用。

初始化中的新船对玩家、生产与战斗不可用，不能生成一半就开始运行。禁止载入后自动恢复开火或高速运动。玩家与酒狐实体不照抄事故位置；玩家安全安置，酒狐从独立角色档案绑定新船。进程在任一步骤中断，重启时根据事务状态继续或撤销，重试同一次请求不会多生成一艘。

## 酒狐船长

酒狐是持久的角色身份，船上终端或人物实体是交互载体。主艇被摧毁不会删除角色记忆；角色实体死亡、卸载或更换表现方式也不产生多个酒狐。

| 层次 | 首版职责 | 后续扩展 |
| --- | --- | --- |
| 船况与对话 | 报告深度、裂纹、进水、能源和下一步建议 | 航海日记、关系变化、事件对话 |
| 基础操控 | 玩家指定深度、停止托管、返航提示 | 定向、低速泊船、姿态与速度控制 |
| 探索任务 | 接受明确任务，检查设备与海域准入条件 | 航点、测绘、打捞、救援和调查任务链 |
| 战斗协同 | 先预留目标与火控接口 | 普通敌人防御、Boss阶段响应、接应玩家 |

先以本地规则/状态机实现可靠行为。以后即使接入对话模型，也只输出白名单内的高层意图，由服务器验证和执行；不能直接让自由文本调用恢复、删船或施力接口。

每个控制通道只允许一个当前控制者。手动接管优先，AI控制必须通过已安装且可用的推进、泵、舵和传感器。Deep Seas 自带定深控制与自研控制器不能同时争夺垂直运动。它的海床跟随不能保证穿洞、跨维度、长距离避障和水平返航，需由自研航线系统补足。

主艇未加载时面板显示最后已知状态和时间，不伪装成实时数据。初版无人在线不持续出海战斗；需要远程托管时再做有限加载票据、能源预算和停止条件，避免为实时监控常驻加载整片海洋。

## 开发结构和顺序

继续使用同一 Java 正式开发工程。先在自研 Mod 内划分 fleet、dock、snapshot、telemetry、captain、compat 等包；不另建独立调试程序。Sable、航空学、Deep Seas、Power Grid 各有适配器，自研业务通过自己的接口调用它们。当前 Gradle 中多数 Mod 仅为 localRuntime，开始写 Java 适配前应补上正确的编译期 API 依赖，并锁定版本。

| 阶段 | 可交付内容 | 进入下一阶段的验收条件 |
| --- | --- | --- |
| 0 接口验证 | 同一工程中装配一个小型密闭潜艇原型，读取速度、质量、船况 | 已装配载体可定位；装卸、重启和分裂身份能够追踪 |
| 1 保存恢复 | 服务器端快照、校验、停机重建 | 方块、容器、压载、胶水/活动部件和电线逐项往返测试；不支持项明确拒绝 |
| 2 唯一主艇 | 身份登记、代次、状态机、船坞终端 | 多人并发点击、未加载旧艇、崩溃中断均不复制主艇 |
| 3 正式主艇与改装 | 建造首台主艇、改装托管、校验和撤销 | 失败恢复结构与材料一致，玩家可继续下一次改装 |
| 4 损伤与恢复 | 船况仪表、危急记录、损毁重建 | 超深、爆炸、关键设备损坏和瞬时删除有明确恢复点与物资结算 |
| 5 酒狐出海 | 报警、定深、任务提示、手动接管 | 一次离港、潜航、故障处理、返港的完整冒险可重复运行 |
| 后续 | 自主航线、武器、Boss协同、子艇 | 在可靠船体与档案基础上逐项接入 |

第一目标不是做出庞大的全功能潜艇，而是验证“装配 → 出航 → 保存 → 受损 → 回船坞恢复 → 重启仍唯一”。这个闭环通过后再扩展外观、房间和装备，能避免后期重建整套船体。

## 关键验收场景

- 相同快照恢复两次、两名玩家同时点恢复、原艇在未加载区块：最多一个有效主艇代次。
- 改装前后各含不同库存，期间尝试拆下物品、管道输出、机械臂转移：取消后资源不增不减。
- 已连接岸电、带转动轴承与胶水、压载非空、电线跨子载体：连接完整恢复或提前明确拒绝。
- 正常卸载、换维度、拆装与分裂：不得误判损毁；第一版未支持跨维度时明确禁止该操作。
- 超深裂纹到内爆、普通爆炸一次摧毁核心、断电后重启：最后已提交设计仍可用，事故日志不冒充完好备份。
- 恢复中途退出，磁盘写满、校验失败、缺失Mod：不会消费两次材料、生成半艘可活动的船或损坏原档案。
- 恢复完成后，酒狐记忆和已领奖任务不回档，玩家背包不复制；旧残骸不能与重建船重复兑现相同物资。
- 典型与最大允许尺寸的主艇分别测 tick、舱室扫描、快照停顿、内存、磁盘增长和重建用时，再确定正式上限。
