# 主潜艇系统开发文档

更新日期：2026-10-14。里程碑：M1.1，唯一主艇登记、三项资格检查与中央控制器设备识别。使用现有 `mods/dbv-world` Java Mod、VS Code 和正式开发客户端，不新增独立调试程序。初版不自动建造主潜艇，不替换起始岛存档。

唯一性目前指**自研登记表只接受一个主艇身份**。检测到已加载身份副本或代次冲突会报警，不会自动销毁或停用玩家复制的物理载具；严格的旧艇清退需要后续恢复事务。当前登记通过服务端公共入口执行下面三项资格检查，失败时不会创建身份文件。船坞部署尚未实现，接入时必须复用同一检查，不能只在界面限制。推进设备不属于资格门槛。

## 已确认：中央控制器与主潜艇资格

2026-10-14用户确认：复用Deep Seas 3.3.0的船载电脑（Onboard Computer，`create_submarine:command_sub`）作为中央控制器，后续在它的功能基础上扩展，不另设必须同时安装的自研控制器方块。

主潜艇首次登记、船坞改装验收及部署必须同时满足三项条件：

1. 同艇存在有效中央控制器，即上述船载电脑。
2. 同艇具有能向目标密闭舱室供氧的氧气制造系统；不能只检查方块是否存在，也不能将创造模式供氧器默认等同于正式生存制氧系统。
3. 同艇具有有效密闭空间，且与供氧系统服务的舱室对应。

这三项是潜艇资格条件；世界唯一登记与防复制仍独立执行。设备或舱室尚未加载、检测尚未完成时显示待检测，不放行，也不误报设备损坏。已经登记的主艇在航行中破舱、断氧或控制器损坏时保留永久身份，记录故障供维修和恢复，不清空登记槽。

螺旋桨、武器、声呐、动力和储物设备属于可选能力。中央控制器后续汇总其类型、位置、数量与可读取的工作状态；缺少某项只影响对应能力，不增加主艇资格门槛。设备必须归属于该艇，不能按距离把码头或邻艇设备算入。

扩展采用自研Mod适配器与组合：保留Deep Seas现有潜航、压载、声呐和诊断行为，增加资格检查、设备清单、报警、船坞事务入口与酒狐交互。设备识别和设备控制分开适配；发现武器不等于已经支持瞄准和开火。未知设备显示未适配，不伪造运行状态。中央控制器是交互入口，永久身份及档案仍由世界级服务保存，不以方块存在与否决定档案存续。

当前已实现资格检查和聊天式设备清单入口，未实现独立图形面板、武器操控或船坞部署。历史M1实心铁块验收不再适用；使用下述qualification脚本进行当前版本验收。


逻辑调用为：管理员命令或服务器tick → FleetModule → 领域登记与持久化 / 物理适配器 → 现有Mod。所有游戏对象只在服务器线程访问；后台线程不遍历世界。领域与JSON存储不引用Minecraft类，便于独立测试。当前适配器将Sable载体传到模块及命令边界，后续扩展多载体时收敛为自有句柄，避免跨层依赖继续扩大。

注册入口从现有 `DeepBlueVoyageWorld` 调用 `FleetModule.initialize()`。按MinecraftServer隔离运行状态，在服务器启动时读取登记，停止时清理缓存；不同存档不会共用静态主艇记录。

依赖以已经安装的版本为准：增加Sable、Sable Companion、Deep Seas的编译期依赖，继续由原运行依赖加载。没有新增玩家内容Mod，也没有将物理引擎打入自研JAR。Sable Companion按[官方开发说明](https://github.com/ryanhcode/sable/wiki)从作者Maven解析；在NeoForge元数据中明确要求Sable 2.0.6与Deep Seas 3.3.0。升级这两个版本必须先核对适配器。

## 数据模型和文件

登记路径：`runtime/client/saves/<世界>/dbv/fleet/registry.json`。该路径只保存身份，**不是船体备份**；后续完整档案仍按玩法方案放入 `dbv/vessels/<vesselId>/`。

```json
{
  "schemaVersion": 1,
  "flagship": {
    "vesselId": "永久UUID",
    "bodyId": "Sable载体UUID",
    "dimension": "minecraft:overworld",
    "name": "主潜艇名称",
    "generation": 1
  }
}
```

名称限制为1～64个Java字符且不含控制字符；维度必须为资源标识，代次为正整数。读取拒绝未知格式、缺失字段、非法身份、非整数代次及过大的元数据文件。原档案解析失败时不会默默视为“未登记”。

创建流程：服务器线程校验 → 独占创建 `registration.lock` → 检查没有既有登记 → 写 `registry.pending.json` 并force落盘 → 原子移动为登记文件 → 关闭并删除锁 → 写入载体命名空间标签。文件系统不支持原子移动则报错，拒绝退回到半写入主档案的方式。它提供首次登记的一致性保护，不是完整世界或船体的断电备份保证。

发生中断时保留锁和临时文件供核对；没有提供“忽略错误重新创建”命令。若登记文件已成功写入而载体标签尚未保存，后续仅给登记中精确匹配的bodyId补回标签。不要在运行期间手动删除登记文件或锁文件；处理故障前保留整个世界及 `dbv` 目录。

载体标签存于Sable `user_data` 的 `dbv_world:flagship` 子节点，只包含vesselId和generation；更新时复制并保留其他Mod的数据。登记表是主权威数据，标签用于验证，蓝图复制出来的标签不会获得新的主艇身份。

## 状态和观测语义

| 状态 | 意义 | 当前响应 |
| --- | --- | --- |
| UNREGISTERED | 当前世界尚无登记 | 管理员可登记一个已加载载体 |
| ACTIVE | 精确绑定载体已加载且身份一致 | 读取质量、缓存速度与可用的压力数据 |
| NOT_LOADED | 没有找到已加载的绑定载体 | 保留登记；不认定损毁，不开放第二次登记 |
| IDENTITY_CONFLICT | 发现身份副本、错误代次或维度不符 | 显示待核对，不改写权威身份 |
| ADAPTER_ERROR | 物理或压力适配读取失败 | 显示失败，不以缺少读数触发损毁 |

“ACTIVE”只表示身份和载体可读取，不等于健康、可航行或密闭。质量使用Sable的kpg单位；速度暂显示引擎缓存数值，不宣称已标定为真实m/s。Deep Seas未登记/初始化舱室时，深度、裂纹和破舱显示未知，不能用0和false假装安全；已初始化读数仍受上游缓存更新节奏影响。

每20tick在服务器线程枚举已加载载体，不主动加载远海区块。当前没有完整伤害接管、永久事故记录或全量船体扫描。状态变化记录日志；查询命令会即时重新采样。大量载体服务器后续需要事件索引和进一步性能评估。

## 开发者使用

在仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\dev.ps1 build
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\dev.ps1 run
```

进入同一开发客户端，先使用现有装配工具建成一个Sable载体。以下命令仅限权限等级2及以上：

```text
/dbv flagship candidates
/dbv flagship inspect <Sable载体UUID> [页码]
/dbv flagship register <Sable载体UUID> <主艇名称>
/dbv flagship status
```

候选命令只列当前维度已加载载体，最多显示30项。登记为管理员开发操作，不会自动生成潜艇，也不会按名字或距离替玩家选择载体。已有登记时拒绝再次登记；当前没有reset、restore或delete命令。尚未装配载体时可以运行status，但不能凭建筑方块直接登记。

## 验证和复现

`tools/dev.ps1 build`包含JUnit测试。资格测试遍历三个条件与待检测状态的16种组合；另有9项登记测试覆盖中文名称持久化、重复登记保护、并发请求单胜者、损坏档案保护、中断锁、未知schema/小数代次拒绝、世界隔离、单槽限制与非法身份。测试不需要游戏界面；JUnit和Gson仅添加为测试依赖。

历史M1验收（资格检查加入前）使用正式开发客户端中的独立验收存档副本 `DBV-Fleet-M1-Acceptance`，不会覆盖 `DBV-Island-v1`。历史脚本为 `fleet-client.js` / `fleet-server.js`，保留供追溯，不应在当前版本执行。脚本会自动进入指定副本，装配27块铁块的Sable载体，登记一次，验证重复登记、质量、未知压力、身份冲突、权限和保存，然后自动退出；第二次启动验证重新读取原身份。铁块载体只是接口验收对象，不是正式主潜艇。

这些脚本属于测试资源，不随主JAR或整合包安装。验收完成后必须移走客户端目录里的临时脚本，避免影响下次正常游玩。成功标记为日志中的 `DBV_FLEET_TEST COMPLETE`，不能只用“客户端能打开”替代功能验收。

## M1.1检查与设备清单

- 普通右键保留Deep Seas原有电脑功能。潜行右键显示本艇资格与设备，普通玩家可用；每秒最多检查一次，重复操作翻页，10秒不操作后回到第一页。
- 管理员可使用`/dbv flagship inspect <UUID> [页码]`检查指定已加载载体。每页12条，列出类别、方块ID、相对船体最小边界的位置与已适配状态；返回值1表示资格通过，0表示不通过或检查失败。坐标随船体边界修改可能变化，不作为持久设备ID。
- 扫描仅遍历该Sable船体已加载区块的非空区段，逐项复核所属载体，不加载远海区块。尚未支持把嵌套子载体自动合并为主艇设备。
- 三项检查读取同艇船载电脑、电解器、扩散器及Deep Seas舱室缓存。电解器需开启、水至少10mB、储能至少250FE；氧气满罐可视作待机。扩散器需有氧、红石供电、完成100tick启动，并邻接有效且未破损的密闭舱室，舱内至少有不含流体的空间。
- 舱室扫描未完成、结构变脏、缓存超过220tick或船体区块缺失时拒绝登记，提示稍后重试。检查是瞬时状态验收，不追溯扩散器储氧来源，不验证整条管路流量或持续供氧时长；续航及管网诊断属于后续功能。
- 已分类Deep Seas设备：电脑、电解器、扩散器、创造供氧器、螺旋桨、水推进器、舵、水雷、声呐、压载舱/通气口、泵控制器、气闸及报警器。其他方块实体列为未适配设备；不猜测其运行状态。武器当前只识别水雷，不包含自动开火。
- 资格与永久身份分离：停机、破舱、拆除电脑后可检查到不合格，但不会清除已有身份。`ACTIVE`仍只表示载体与身份可读取，具体资格使用inspect查看。

当前自动验收使用`qualification-client.js` / `qualification-server.js`，临时放入正式客户端KubeJS对应目录，只操作`DBV-Fleet-Qualification-Acceptance`地图副本。夹具直接给真实电解器和扩散器注入水、能量及氧气，验证真实设备状态和舱室扫描；不是管路输送或长期续航测试。只允许日志出现`DBV_QUAL_TEST COMPLETE`且无FAIL/ERROR时判为通过。测试后移走临时脚本并归档副本，不改动正式起始岛。

2026-10-14 M1.1实际验收通过：10项JUnit测试（含16种资格组合）、首次客户端26项断言、重启客户端24项断言。覆盖真实制氧、同艇设备识别、附近设施排除、普通/潜行交互事件、缺水/断电/断氧/失去红石/缺少电脑、破舱与修复、重复登记、重启身份保留，以及移除推进和武器后仍合格。首次和重启均出现成功标记。证据见[首次验收](../../outputs/fleet-qualification-20261014/first-run.log)、[重启验收](../../outputs/fleet-qualification-20261014/reopen.log)、[验证结果](../../outputs/fleet-qualification-20261014/verification.json)。临时脚本已移出客户端，验收存档归档至`runtime/backups/DBV-Fleet-Qualification-Acceptance`。未验证多页设备清单的大型船体性能、真实管路持续输氧或武器操控。
