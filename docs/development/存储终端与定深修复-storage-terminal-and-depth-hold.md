# 存储终端与定深修复

适用：Minecraft 1.21.1 / NeoForge，现有32块压载、双柴油机的灯笼鱼型主潜艇。

## 为什么目标1米却沉底

正式存档副本复现了控制器约45米、目标1米、四个泵均已连接、柴油机有转速，但压载泵处于HOLD的情况。初始艇实测质量约2833，而32块压载的默认标称总承载为2400；更关键的是，上游控制器从理想升降速度反推含水比例，没有根据这艘船实际移动速度修正，结果在尚未到达目标时停止排水。

只提高承载参数并不足以修复定深：试验中能上浮，但仍在错误深度停止调水。因此同时调整：

- `ballastLiftPerTank` 从75调整为300，为此铁壳样艇提供升降余量。这是整包的Deep Seas全局参数，其他使用该配置的潜艇也会受影响，并不代表重量限制已设计完成。
- 只有已登记的主潜艇使用实际反馈控制。每5 tick采样控制器世界坐标，用位移/游戏时间计算真实垂直速度；根据目标深度、实际速度及加速度阻尼输出压载含水目标，再让原生泵执行注排水。
- 不使用传送、额外悬浮推力或强制速度赋值。停止上游主艇近目标的直接冲量修正，避免两个控制器互相干扰。非主艇继续使用上游控制器。
- 没有可靠海面或压载信息时保持停止调水；采样中断会清除速度滤波状态，避免沿用过期状态。

`config/submarine-balance.json` 管理承载参数。`tools/dev.ps1 prepare/run/debug` 会调用 `tools/sync-submarine-config.ps1` 同步到正式客户端，只更新这一项并首次保存原配置。直接运行Gradle或发布整合包时，应使用 `pack/overrides/config/create_submarine-server.toml`。

## 可交互存储终端

潜行右键中央控制器，或使用舱内信息面板，点击“存储终端”。上部为船内容器槽位，下部为玩家背包，支持普通点击、右键分堆、拖动及Shift快速转移，每页54格。物品直接保存在实际容器中，不另造一份虚拟库存；每次点击处理后更新主艇独立JSON档案。

首版按实际槽位分页，尚未合并同类物品总数，也不含AE的网络合成功能。读取原版存储容器及Create保险库的可修改物品能力；生产设备的升级槽和内部材料槽不纳入。保险库只从多方块控制器读取一次。锁定容器遵守原有开启权限。

翻页时须先放下鼠标所持物品。离开主艇附近、进入改装、载体替换、容器拆除或能力失效时停止交互；不通过客户端提交物品数量。原有“存储备份”页仍保留手动备份/恢复入口。

## 验证范围

验收使用正式世界副本，不将测试钻石、木桶或玩家位置写回正式世界。记录保存在 `outputs/depth-terminal-20261015/`。测试覆盖真实菜单点击、Shift转移、翻页、距离失效和独立JSON扫描；不能视为所有第三方储物模组的兼容认证。完整燃油续航、超重改装和暴风/洋流扰动仍需后续测试。

最终自由航行验收：从原存档沉底状态启动，目标1米时控制器实际深度0.904米；改设15米后实际14.910米，全程未系泊。Deep Seas整数深度显示仍向下取整，因此0.904米可能显示0米，控制算法使用未取整的实际深度。构建及29项单元测试通过。右键分出32个钻石后合并回64个、玩家背包与船内容器互转、翻页和离艇断开均已通过。早期仅增加承载和第一版反馈的失败记录一并保留。

重新运行 `tools/dev.ps1 run` 即可加载代码和配置；现有世界不需要重新生成。正式存档未被验收副本替换。新增或扩建储物容器后，重新打开终端以重新发现槽位。
